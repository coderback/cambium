**A mutation of mine was itself wrong:** my first "preflight runs after `load_dgraph`" mutation

test catches it. A surviving mutation is only evidence if the mutation is real.

## Session 37 — the environment rule, rejected twice

**The gap.** ADR-013 clause 3 fixes a bit-for-bit bar and says nothing about the stack it is measured
on. ADR-005 already settles the principle; ADR-008 clause 4 applies it; the DGF-1 check inherited
neither, and printed `REPRODUCED … bit-for-bit` with no environment statement.

**Draft 1 (`bd422c3`), an in-place amendment to ADR-013 — rejected, withdrawn today.** It created an
exception to ADR-008 clause 2's no-retry rule inside a document declaring that rule *inherited, not
re-opened*; its own items made each other unreachable (refusing before the run means no comparison and
no row, so its INCONCLUSIVE row and its "cite both rows" were impossible); it borrowed ADR-008's
"re-establish the reference" escape, which does not exist here because DGF-1's reference is one frozen
row and regenerating it *is* the check; and it attributed "certifies nothing" to ADR-008 clause 4,
which actually prescribes a degraded-but-interpretable result. Struck from ADR-013 today, not made to
wait on its replacement.

**Draft 2 (`d7c453e`, ADR-014) — also rejected.** Two reviews, both blocking, and the first finding is
one I had suspected when commissioning them:

- **Clause 3 could never run.** It put environment provenance in `base_cfg`, which `resolve_config`
  hashes in full — measured `d825a002…` → `854552d6…`, so the pre-run guard would refuse forever.
  Wrong a second way too: `base_cfg` keys never reach `metrics_json` at all, only the four in
  `PROVENANCE_KEYS`. My inference from `experiment` was backwards — it arrives *despite* `base_cfg`,
  via an allow-list. Fix: a non-hashed `extra_metrics` channel on `run_dgf1`.
- **I repeated the error I had just rejected.** ADR-013 clause 3 says no later run may rely on the
  trainer until the check passes; ADR-014's clause 5 let Gate 3 proceed anyway. I moved the carve-out
  from ADR-008 clause 2 to ADR-013 clause 3 rather than removing it, and never wrote the sentence
  admitting it. A laundering path exists: FAIL → permanently unattributable → upgrade a package →
  now REFUSED → declare unobtainable → proceed.
- **Clause 1 needed a parser that does not exist.** `_pinned_versions` reads only `[pip freeze]` (52
  entries); `python`, `cudnn`, `compute_capability`, `gpu` are all absent from it.
- **Clause 6's premise was false.** I wrote that gate batches compare arms run against each other;
  Gate 1's arms came from **at least two** invocations, 00:37–01:55 at commit `09c6e726`.
  (Corrected 2026-09-15: this entry first said "three". `run_dgf1_floor.py:108` loops over
  `feature_sets` inside one invocation, so both XGBoost arms may be a single run.)

**Two real findings about the code, not the document:**
1. **The CPU-fallback hole is live.** `environment_drift` guards its GPU/CUDA checks behind
   `torch.cuda.is_available()`, and `resolve_device("auto")` silently falls back to CPU. Lose CUDA and
   the check reports no drift, trains on CPU, fails every float comparison, and records a sound
   trainer as a regression under a no-retry rule.
2. **A second route to the same place:** `device: auto` lives in `config.yaml` but is returned by
   `dgf1_hparams()`, not `dgf1_base_config()` — so it is in neither the hashed config nor the row.
   Editing that one line to `cpu` passes the hash preflight untouched.

**The fix I had missed.** The stored pilot row is not the only possible reference. If the stack has
drifted, run the pre-ADR-013 trainer *and* the new one on the current stack and require those two to
match — same environment on both sides, so the only difference is the code. That is what ADR-008 did
by freezing pre-refactor. It removes the deadlock, and with it the entire clause that failed review.

## Session 38 — ADR-014 withdrawn after four drafts; the re-certification PASSED

**ADR-014 withdrawn, undecided.** Four drafts, four adversarial rejections, all for one cause: each
invented a deadlock — *what if the stack has drifted and the check can never pass?* — and then, because
that deadlock was intolerable, smuggled in a route around it. Draft 4's routes were a *Revisit when*
that pre-authorised dropping a compared field by self-adjudicated amendment; a pin that nothing
hashes, under a clause claiming an edit would be "detectable from the row alone"; and an outcome table
that decided PASS on the environment fields while omitting the stored-row comparison. **The deadlock
was speculative in all four: the stack matched the pin the whole time.** Four documents about the
failure of a check nobody had run, in a situation where it would pass. The ADR is kept as a withdrawn
record of the drafts and of eight findings that were measured rather than argued.

**Two errors of mine in draft 4, recorded because they are the kind this programme exists to catch:**
it asserted `run_dgf1_gnn.py` "already imports from `check_extract_regression`" (it does not — the
claim would have pulled ELL-1 adapters into the DGF-1 gate runner), and it cited "suite 238 → 251"
twice as evidence for work preserved in no commit, in the same document that rejected an earlier draft
for resting on "console text no artifact preserved". The suite is 238.

**The re-certification PASSED** (ADR-013 clause 3), run `dgf1-20260915T151348Z-0d390b65` at commit
`399dd7ff`, clean tree, 572.1 s.

- Against the validation pilot's seed 0 `dgf1-20260913T232506Z-1acd5067`: **19 metric fields and 4 row
  columns bit-for-bit**, score-file SHA-256 included. Verified independently from the registry
  afterwards, not from the console: `compare_repro` → no problems, and the `.npz` **on disk**
  re-hashes to the row's value.
  - `fraud_auc` 0.7810034416168538 · `fraud_auprc` 0.04127410516906848 ·
    `scores_sha256` a33105f7fb2c50adc7257779b3f17870374ce890e0e82fbb9817479b9f797f3b — all identical.
- **The row carries no `window_only_*` or `first_appearance_*` key**, confirming ADR-013 clause 3's
  removal on real data, not just on the synthetic fixture.
- It is the only `repro_check` row in the registry.

**How this result is stated, and it is not unconditional** (ADR-005: reproducibility is
same-environment). **Reproduced on a stack matching ADR-008's pin**, measured immediately before the
run: `environment_drift` → none; torch 2.13.0+cu126, torch-geometric 2.8.0.post1, pyg-lib
0.8.0+pt213cu126, numpy 2.5.1, scikit-learn 1.9.0, python 3.13.5, cuDNN 91002, CUDA 12.6, RTX 3050 Ti
Laptop GPU, compute capability (8, 6), resolved device **cuda**; pin sha256
`7b732221deac21fe7bcf708fee5f725b025f9d5d5f3dece13d6b3aa2f6412c4d`. The pin was captured 2026-07-26
and the pilot ran 2026-09-13 recording no package version, so this says *the stack matched the July
pin*, never *it matched the pilot's stack*. That gap is unclosable and is not closed.

**What it unblocks.** ADR-013 clause 3's rule — no later DGF-1 run may rely on the trainer until the
check passes — is satisfied. Gate 3's ADR cites this run id and this qualification, not the outcome
alone.

**Still latent, and still a code defect rather than a decision:** if CUDA becomes unavailable,
`environment_drift` reports nothing (its GPU checks sit behind `torch.cuda.is_available()`),
`resolve_device("auto")` falls back to CPU, and a sound trainer would be recorded as a regression.
Editing `device:` in `adapters/dgf1/config.yaml` reaches the same place with no driver failure. It did
not bite today because the device resolved to cuda.
